## 0. Контекст

Discord Activity — интерактивный редактор карты фэнтези-мира для узкой команды
разработчиков/участников проекта. Работает прямо внутри Discord. Не связан с
Minecraft-сервером (никаких координат/claims оттуда не передаётся).

Этот документ — самодостаточное ТЗ. Предыдущая версия проекта (векторные реки/
озёра/моря) была написана в чате Claude и не сохраняется — Claude Code начинает
разработку с чистого листа по этому документу.

## 2. Общее назначение

Редактор политической/географической карты для группы разработчиков мира.
Работает как рисовалка, а не GIS-программа: пользователь выбирает инструмент,
рисует мышью, всё остальное (сглаживание, обрезка границ, синхронизация)
редактор делает сам.

Карта условно бесконечная, можно приближать/отдалять, несколько человек
редактируют одновременно в реальном времени. Просмотр — всем с доступом к
Activity, редактирование — только пользователям с определённой Discord-ролью.

## 3. Сущности карты

```
MAP
├── States (государства)
│   ├── name, color, discord_post_id
│   └── regions[] — через поле state_id у региона
│
├── Cultural Regions (культурные регионы)
│   ├── name, color, discord_post_id
│   └── regions[] — через таблицу многие-ко-многим
│
├── Regions (обычные регионы)
│   └── name, geometry (GeoJSON Polygon/MultiPolygon), state_id
│
├── Point Objects (точечные объекты)
│   ├── icon_type (capital/city/village/fortress/dungeon/cave/resource)
│   └── name, position {x,y}, discord_post_id
│
├── Roads (дороги)
│   ├── road_type (major/minor — "крупная"/"малая")
│   └── geometry (GeoJSON LineString)
│
├── Bridges (мосты)
│   └── geometry — короткий отрезок, создаются АВТОМАТИЧЕСКИ на пересечении
│       дороги с водой (см. раздел 5 — вода теперь часть рельефа, не объект)
│
└── Terrain (рельеф — см. раздел 5, заменяет реки/озёра/моря)
    └── Chunks[] — тайлы сетки высот
```

**Убрано из более ранней версии ТЗ**: реки, озёра, моря как отдельные векторные
сущности. Их визуальную роль теперь выполняет рельеф (см. ниже) — вода
появляется автоматически там, где высота ниже уровня моря.

## 4. Регионы, государства, культурные регионы — без изменений от исходного ТЗ

### 4.1. Регионы
- Рисуются свободно мышью: зажал ЛКМ — провёл границу — отпустил
- Автоматическое сглаживание линии (умеренное — деталей не теряет)
- Автозамыкание контура в полигон
- **Умные границы**: регионы не могут пересекаться. Новая нарисованная область
  автоматически обрезается по границе существующих регионов. Если два региона
  соприкасаются — общая граница должна быть единой, без щелей и нахлёстов.
  При рисовании рядом с существующей границей — линия "прилипает" к ней.
- Инструмент **"Расширить область"**: рисуешь новую область — она либо
  примыкает к существующей территории региона (объединяется), либо не
  соприкасается (регион становится многочастным, например архипелаг из
  нескольких островов — это один регион с несколькими полигонами).
- Инструмент **"Уменьшить область"**: обвёл кусок — он вырезается из региона.
  Если регион в результате распался на несколько частей — они остаются одним
  регионом (отдельного инструмента "разделить" не нужно).
- **Вложенные регионы**: регион может быть целиком внутри другого (анклав).
  Это просто свойство геометрии, отдельного режима не требует.
- У обычного региона нет своего цвета и нет Discord-поста.
- Панель выбранного региона: переименовать, расширить, уменьшить, удалить.

### 4.2. Государства
- Не отдельный полигон — объединение регионов (через `state_id` у региона).
- Один регион принадлежит только одному государству либо не принадлежит никому.
- При создании: имя, цвет (палитра произвольного цвета), опционально ID
  Discord-поста с описанием.
- Территория государства на карте — полупрозрачная заливка выбранным цветом,
  граница — тем же цветом.

### 4.3. Культурные регионы
- Аналогично государствам: объединение регионов, свой цвет, свой Discord-пост.
- В отличие от государств, у одного региона теоретически может быть только
  один культурный регион одновременно (упрощение для MVP — как и у государств).

### 4.4. Режимы отображения карты (переключаются кнопками, не мешают рисованию)
1. **Государства** — регионы окрашены по государству
2. **Культурные регионы** — регионы визуально объединены по культурной группе
3. **Регионы** (обычный) — просто границы и названия, без окраски

Точечные объекты, дороги, мосты и рельеф видны во всех трёх режимах одинаково.

## 5. Рельеф (заменяет реки/озёра/моря) — НОВАЯ часть, основной фокус

### 5.1. Идея
Вместо ручного рисования рек/озёр/морей как отдельных векторных объектов —
редактируемая **карта высот** (heightmap) с кистью повышения/понижения рельефа.
Вода появляется автоматически там, где высота ниже заданного порога (уровня
моря). Визуальный стиль — контурные изолинии (как на топографических картах),
пример-референс приложен пользователем в чате (тёмный фон, светлые извилистые
изолинии, эффект лёгкого свечения/глубины на стыке рельефа и воды).

### 5.2. Хранение данных
- Мир рельефа разбит на **чанки** (тайлы), например 64×64 ячейки на чанк —
  по аналогии с Minecraft: подгружаются только чанки в видимой области,
  остальное не хранится в памяти клиента.
- Каждая ячейка чанка — целое число высоты (например Int16: диапазон с запасом
  выше/ниже уровня моря).
- Хранение в Supabase: таблица `terrain_chunks` (`map_id`, `chunk_x`, `chunk_y`,
  `heights` — **bytea**, не JSON — это на порядок компактнее и экономит
  бесплатный лимит трафика Supabase).
- Глобальный параметр карты `sea_level` — порог высоты, ниже которого рендерится
  вода. Хранится в таблице `maps`.

### 5.3. Рендер — GPU-шейдер (не CPU-пересчёт)
- Каждый загруженный чанк — `RenderTexture` в PixiJS, хранит высоты как значения
  пикселей текстуры.
- Один fragment-шейдер поверх текстуры высот в реальном времени:
  - **Изолинии**: `fract(высота / шаг)` около 0 — белая линия; сглаживание через
    `fwidth()`, чтобы линия не "лесенкой" на любом зуме.
  - **Мягкое освещение по градиенту высоты** (склон круче — темнее) — для
    ощущения объёма, как на референсе.
  - **Вода**: там, где высота < `sea_level`, подмешивается синий цвет
    автоматически. Никакого отдельного объекта "море"/"озеро" в БД нет.
- Работает быстро независимо от размера всего мира — шейдер считает только
  видимые пиксели экрана, не весь мир целиком.

### 5.4. Кисть
- Инструмент "Рельеф" — круглая кисть с настраиваемым радиусом и силой.
- Пока зажата ЛКМ — кисть рисует прямо в `RenderTexture` чанка (на GPU) в режиме
  "прибавить" (повысить) или "вычесть" (понизить, например с зажатым модификатором
  или отдельной кнопкой-переключателем силы, аналогично переключателю дороги в
  остальной части ТЗ).
- Мягкие (растушёванные) края кисти — без резких ступенек рельефа.
- Пока кнопка зажата — рисование полностью локальное (без обращений к серверу).

### 5.5. Синхронизация (важно для бесплатного тарифа)
- **Не** отправлять каждое микро-изменение кисти на сервер (быстро сожрёт лимит
  трафика бесплатного Supabase).
- Раз в ~1 секунду, пока пользователь рисует, и обязательно при отпускании
  кнопки — считать (`readback`) изменённый регион текстуры обратно в массив
  чисел и отправить на сервер **только реально изменившиеся чанки**, бинарно
  (`bytea`), не JSON.
- Другие пользователи получают через Supabase Realtime не поток мазков, а
  редкие снепшоты изменённых чанков (примерно раз в секунду). Небольшая
  задержка (~1 сек) для карты мира не критична.

### 5.6. Взаимодействие рельефа с остальными объектами
- Регионы/государства/точечные объекты/дороги рисуются **поверх** рельефа
  (отдельный слой сверху, z-order), рельеф на их логику не влияет.
- **Мосты создаются автоматически**: когда нарисованная дорога проходит по
  участку, где рельеф ниже `sea_level` (то есть по воде), в этом месте
  автоматически создаётся объект "мост" (короткий отрезок). Пересчёт делается
  по высоте рельефа под линией дороги, не по пересечению с векторной рекой
  (реки больше нет как объекта).

### 5.7. Порядок реализации рельефа (внутри общего плана, см. раздел 14)
1. Один чанк: `RenderTexture` + кисть, рисующая в него локально — проверить,
   что ощущается хорошо физически, прежде чем усложнять
2. Шейдер поверх чанка: изолинии + вода по `sea_level` — сверить с референсом
3. Несколько чанков рядом + подгрузка/выгрузка по видимой области
4. Readback + сохранение изменённых чанков в Supabase (bytea)
5. Приём чужих чанков через Realtime, обновление текстур
6. Проверка корректного z-order с регионами/дорогами/объектами, авто-мосты

## 6. Точечные объекты — без изменений от исходного ТЗ

- Типы: столица, город, деревня, крепость, данж, подземелье, ресурс
- Векторные иконки (без внешних картинок на старте; можно заменить позже)
- Масштабируются под зум: сильно отдалено — маленькая точка, приближено —
  детальная иконка; название показывается постоянно при сильном приближении,
  иначе — по наведению
- Можно перетаскивать на карте, привязка к государству/региону не жёсткая
- Discord-пост опционально — содержимое подтягивается и показывается в панели

---

## 7. Дороги и мосты

- Два типа дороги — крупная (щебёночная) и малая (просёлочная), визуально
  различаются (толщина/цвет линии)
- Дорога рисуется свободно, не обязана ничего соединять
- Может пересекать другие дороги и рельеф/воду произвольно
- **Мост** — не создаётся вручную; появляется автоматически там, где дорога
  проходит по воде (см. раздел 5.6)

## 8. Discord-интеграция

### 8.1. Activity shell
- Discord Embedded App SDK (`@discord/embedded-app-sdk`)
- Открывается прямо в Discord, занимает доступное пространство

### 8.2. Авторизация и права
- OAuth2-код с фронтенда → обмен на токен **на сервере** (Supabase Edge
  Function, `client_secret` никогда не попадает в браузер)
- Проверка роли пользователя на сервере (через бот-токен, тоже в Edge Function)
- Право редактирования = наличие определённой Discord-роли на сервере;
  сложная система гранулярных прав ("может рисовать регионы, но не города")
  не нужна — одно общее право "может редактировать"
- Без нужной роли — карта доступна только для просмотра

### 8.3. Discord-посты как описания
- У государств, культурных регионов, точечных объектов — поле `discord_post_id`
- Получение текста поста — через Edge Function с бот-токеном (правило Discord:
  ID стартового сообщения ветки/форум-поста совпадает с ID самой ветки)
- Показывается во всплывающей панели объекта

### 8.4. Сетевые особенности Activity (важно, часто забывают)
Внутри Discord Activity браузер работает в песочнице — прямые запросы к
внешним доменам (например `*.supabase.co`) блокируются. Нужно:
- В Discord Developer Portal → Activities → URL Mappings → добавить маппинг
  (например префикс `/supabase` → `<project-ref>.supabase.co`)
- На фронтенде вызвать `patchUrlMappings` из Embedded App SDK при старте —
  тогда обычные вызовы к `supabase.co` автоматически проксируются через Discord

## 10. Интерфейс

- Карта занимает всё доступное пространство, элементы интерфейса — плавающими
  панелями поверх, не загромождать вид
- **Никакого отдельного режима "Обзор"/"Перемещение"** — выбор объекта кликом
  работает всегда, независимо от активного инструмента рисования
- **Перемещение по карте — только зажатым колёсиком мыши** (среднее нажатие +
  drag), не левой кнопкой. Зум — обычное вращение колёсика.
- Панель инструментов (ровно этот список, без лишнего):
  **Новый регион · Новый объект · Новое государство · Культурный регион ·
  Рельеф (кисть) · Дорога** (переключатель крупная/малая по повторному клику,
  с визуальным индикатором — точки рядом с текстом)
- Панель выбранного объекта — контекстные действия конкретно для этого типа
  (переименовать/удалить/специфичные для типа — расширить/уменьшить для
  региона, сменить цвет для государства, и т.д.)
- Никаких системных `prompt()`/`alert()` для форм ввода — только нормальные
  встроенные формы (модальные окна в интерфейсе приложения)

## 11. Совместное редактирование

- Все изменения — сразу видны другим пользователям (кроме рельефа, где
  синхронизация батчами раз в секунду — см. раздел 5.5, это осознанный
  компромисс ради бесплатного тарифа)
- Без ручного сохранения — карта единая рабочая версия
- Курсоры других пользователей — не обязательны
- Конфликты — "кто последний записал, тот и победил" (простая модель,
  сложная система разрешения конфликтов не нужна на этом этапе)

## 13. Что сознательно не делаем на этом этапе

- Связь с Minecraft-сервером, координаты, claims
- Полноценный GIS-инструментарий, ручное редактирование каждой вершины как
  основной способ работы
- Гранулярная система прав (только общее "может редактировать")
- Обязательное отображение курсоров других пользователей
- Сложное разрешение конфликтов одновременного редактирования

## 14. Рекомендуемый порядок разработки для Claude Code

1. Каркас Discord Activity (пустая страница внутри Discord, OAuth заготовка)
2. Карта: бесконечный холст, зажатое колёсико = перемещение, колёсико = зум
3. Регионы: рисование, сглаживание, умные границы, вложенность, панель объекта
4. Государства и культурные регионы: создание, назначение регионов, три режима
5. Точечные объекты: типы, иконки, LOD, перемещение
6. Дороги (два типа)
7. **Рельеф**: по подпунктам из раздела 5.7 — это самая рискованная с
   технической точки зрения часть, закладывать на неё больше времени и
